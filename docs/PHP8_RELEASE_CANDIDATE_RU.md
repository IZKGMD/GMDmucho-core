# MuchoCore PHP 8 — подготовка полного релиза

Дата проверки: 13 ноября 2026 года. Этот документ относится к **текущему
исходному коду main**, а не к старому опубликованному тегу `v1.1.0`.

## Что уже подтверждено

- Комплексный CI на коммите `1d65288171c9b05e909f4715818187539824fe09`:
  Validate, PHP 8 HTTP acceptance, MariaDB 8.2/8.3, совместимые сборки,
  Go и упаковка прошли. Это свидетельство работы автоматических тестов.
- Объединены исправления админки, резервного копирования, загрузки музыки,
  прокси-IP, вебхуков и MuchoProtect (PR #296).
- Есть автоматизированные сценарии первой регистрации владельца, восстановления
  пароля через локальный STARTTLS-стенд, миграций и SQL-восстановления.
  Реальный SMTP-провайдер и публичный VPS этими тестами не проверяются.

## Почему статус пока не Stable

По `tests/protocol/endpoint-contracts.json` на эту дату:

- 166 инвентаризированных эндпоинтов;
- 160 помечены `inventory_only`;
- 0 помечены `release_gate=true`;
- отсутствует полная верификация настоящими клиентами Windows/Android,
  подтверждение p95, реальное воспроизведение MP3 и проверка чистого VPS.

Число неполных контрактов **не равно** количеству найденных багов.
Полная готовность определяется `php tests/release/v110-endpoint-gate.php`.
Его нельзя обходить сменой `VERSION`, подстановкой синтетических данных
или объявлением HTTP-ответов фактической совместимостью клиента.

## Где взять текущий PHP 8 build для тестов

Workflow **Build Composer vendor archive** формирует архив из конкретного
Git SHA. Результат находится в GitHub Actions → соответствующий запуск
workflow → Artifacts:

- `MuchoCore-PHP8-dev-<git-sha>` — архив исходников PHP 8 с production
  Composer-зависимостями и `checksums.sha256`;
- `muchocore-vendor-php83-<git-sha>` — только vendor-зависимости.

Внутренний ZIP называется `mucho-core-v<version>-dev-<short-sha>.zip`.
Суффикс `dev` намеренный: этот пакет **не является** стабильным релизом.
Сборщик берёт только отслеживаемые Git-файлы, исключает runtime-секреты,
проверяет структуру ZIP и хеши SHA-256.

Для проверки целостности распакуйте artifact ZIP в отдельную папку и
выполните из неё:

```bash
sha256sum -c checksums.sha256
```

Для тестового VPS установка из исходников описана в
`docs/VPS_INSTALL_QUICK_RU.md`. Обновление существующего сервера — отдельная
операция; не запускайте чистую установку поверх рабочего GDPS и не удаляйте
постоянные Docker volumes. Сохраните отдельную проверенную копию SQL,
`.env`, `.secrets`, ключа Cloud Save и файлов `storage/music-public`.

## Что необходимо проверить перед стабильной публикацией

1. **Изолированный VPS:** чистая установка, браузерная регистрация владельца,
   миграции, вход в админку, перезапуск, HTTPS и изменение конфигурации.
   Повторить как обновление без удаления данных и проверить восстановление.
2. **Почта:** реальная SMTP-доставка, одноразовость ссылок, истечение срока,
   восстановление пароля после переустановки, отзыв старых сессий и API-токенов.
3. **GD 2.209:** для Windows и Android с `binaryVersion=51` проверить
   вход, поиск/загрузку/скачивание уровней, таблицы лидеров, комментарии,
   сообщения, облачное сохранение, рейтинги и модерацию. Зафиксировать
   наблюдаемый результат в клиенте и безопасно очищенную метаинформацию.
4. **Музыка:** загрузка оригинального разрешённого MP3, модерация,
   `getGJSongInfo`, выбор ID и реальное проигрывание в редакторе после
   повторного скачивания на новом клиенте. Версии 1.0–1.8 без модификации
   музыкального клиента не должны заявляться как совместимые.
5. **Ресурсы:** повторить нагрузочные тесты PHP-FPM/MariaDB, защиту от
   злоупотреблений, восстановление SQL + MP3, измерить p50/p95/p99 на
   реальном тестовом стенде и зафиксировать принятые пороги.
6. **Артефакты:** убедиться, что релизный ZIP имеет checksums, документацию,
   известные ограничения и план отката, а все обязательные CI проходят
   именно на финальном коммите.

## Политика публикации

`.github/workflows/release-stable.yml` публикует Stable **только**
после полного endpoint gate, native CI, ZIP/checksum-проверок и успешного
Validate на точном релизном коммите. Это относится к любой будущей версии,
а не только к `1.1.0`.

Существующий GitHub Release `v1.1.0` опубликован 27 октября 2026 года,
но его вложенные ZIP-архивы отсутствуют. Исторический тег не содержит
современные исправления `main`; нельзя выдавать его за новую PHP 8 сборку.
